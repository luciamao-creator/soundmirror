## 一、一句话结论

**工程底座已可交付,但产品价值尚未验证。**

现在这套系统能可靠地跑完 7 阶段创作流程、不丢数据、不假装成功、可回放每一步决策。
但它生成的"音乐"是 220/330/440 Hz 的单音,**不是音乐**。
所以:**"这个产品有没有价值"这个问题,现在回答不了。**

---

## 二、这一轮真正发生了什么

上一轮我给的"21/21 PASS"是无效的。这轮为了拿真数字,**挖出 6 个真 bug**:

| # | Bug | 业务影响 | 严重度 |
|---|-----|---------|--------|
| 1 | `TraceRecorder` SQL 少一个占位符 | 决策轨迹**从未落盘**,"可溯源"是假的 | 高 |
| 2 | 3 路生成全失败仍进下一阶段 | **用户看到"可选片段",点开全是坏的** | **高** |
| 3 | 3 个候选音频字节完全相同 | 无法证明工具对参数敏感,等于没生成 | 中 |
| 4 | 空输入走 continue 空转 | Agent 对用户无意义输入不反应 | 中 |
| 5 | 两个 action 不在 catalog | 归档/重置功能实际不可用 | 中 |
| 6 | `AgentDecision.tool_calls` 永远为空 | **接 UI 时前端拿不到 loading 状态** | 中 |

**这 6 个 bug 是被验证机制逼出来的,不是被测试逼出来的。**
上一轮"测试全过"是因为断言太弱;换成更严的断言后,当时的通过率是 **69.7%**。

**这对 PM 意味着两件事:**
1. 之前的"完成度"评估偏乐观,真实完成度更低;
2. 现在建立的验证机制是有效的 —— 它能自己发现我看不见的问题。

### 三个我认为值得单独看的数字

**1. 真 SIGKILL 恢复 = 3/3**

不是同进程丢弃对象,是**真的起子进程、在流程中途 `kill -9`**。
恢复结果:素材 2 条 → 2 条一条不丢、没产生重复 session、全部跑到归档完成。
对应 DB 证据:`artifacts/e10_kill{2,4,6}.sqlite`

**2. 变异测试 = 3/3**

我故意把系统改坏,看断言会不会失败:

| 故意注入的缺陷 | 结果 |
|--------------|------|
| 让 Agent 对任何输入都返回 `continue`(橡皮章) | 决策种类 4 → 2,断言失败 ✅ |
| 拆掉 `ARCHAEOLOGY` 完成条件 | 门禁行为立刻改变 ✅ |
| 清空 voice-clone 拦截词表 | 拦截失效 ✅ |

**这证明阶段门禁、合规拦截、决策区分度是真代码,不是摆设。**

**3. 工具失败不谎报 = 3/3**

故意让 3 路生成全部失败:
- `generation_status` = `FAILED`
- **停在原阶段,不进"片段评估"**
- 每次工具调用都带 `duration_ms` 和 `error` 字段

## 五、关于"方向对不对"的判断

### 我认为对的部分(有证据)

- **阶段门禁** — 变异测试证明拆掉它行为立刻变
- **中断恢复** — 真 `kill -9` 下不丢数据
- **失败不伪装成功** — 工具全失败时停在原地
- **后端解耦** — 换成命名/接口都不同的实现,核心一行不改
- **决策可回放** — 每步落 SQLite,含输入/证据/风险/工具/验证

这几件事做扎实了,意味着**将来换任何音乐模型都不用重写核心**。

### 我不敢下结论的部分

**这个 Agent 到底能不能创作出"像这个人的"音乐,我一行证据都没有。**

现在的证据只说明:**控制流通了、不瞎承诺、不丢数据。**
不能说明:**它有创作价值。**

我倾向于认为骨架方向是对的,但这只是工程判断,**不是产品验证**。

## 六、建议的下一步

| 选项 | 内容 | 回答什么问题 | 成本 | 我的建议 |
|------|------|------------|------|---------|
| **A** | 接一个真实音乐后端,做 10 次完整创作 | "生成的歌像不像" | 需 API key;不确定 Matrix/YuE2 外还有无可用服务 | **首选** |
| **B** | 找 3–5 个人用 CLI 走完整流程,记录反应 | "用户觉不觉得有用" | 需找人;当前 UI 简陋 | 次选 |
| **C** | 补并发测试、trace 回放工具、性能基线 | 降低返工 | 不产生新价值 | 暂缓 |

### 为什么建议 A

缺口 1 是"方向对不对"的**唯一答案**。
C 做得再好也回答不了;B 有价值但依赖当前简陋的 UI,可能测不出真实体验。

**如果 A 证明生成的歌确实不像,整个方案需要重新设计方向,而不是继续打磨。**
这个风险值得优先排除。

### 关于 B 的补充

如果你判断**真实反馈比真实 API 更容易拿到**,那 B 优先也合理。
但建议先花半天把 CLI 界面做得能演示(加 loading 提示、展示 3 个候选、让用户能"换一批"),
否则测出来的可能是界面问题而不是产品价值。
